📋 Synthèse Exécutive

Contexte Stratégique

Pernod Ricard est en pleine phase de transformation data avec la construction de la plateforme Codex sur Snowflake et Azure. Cette plateforme, lancée il y a moins de 7 mois, a vocation à devenir la plateforme data transverse du groupe, remplaçant les 11 plateformes existantes à travers le monde. Le groupe utilise déjà dbt Core pour ~70% de ses transformations, avec une communauté d'environ 100 data engineers répartis dans différentes squads.

💡 Opportunité

Standardiser la qualité des données à l'échelle du groupe et industrialiser la stratégie Data Product, en capitalisant sur l'adoption existante de dbt Core et la modernité de la stack Codex.

🎯 Solution

Migrer vers dbt Cloud pour unifier les pratiques de transformation, de tests et de documentation, tout en apportant une visibilité end-to-end sur les Data Products.

💰 Impact Business

Réduction des coûts Snowflake (15-60% via Smart Execution), amélioration de la productivité des équipes, et établissement d'un framework de qualité unifié pour le projet LEAP.

⚠️ État Actuel & Points de Friction

1️⃣ Fragmentation de la Data Quality

Problème : La qualité des données est gérée en silos avec des scripts ad-hoc, des procédures stockées isolées et des tests dbt disparates. Pas de framework commun ni de responsabilités clairement établies entre ingestion, transformation et data stewardship.

Impact : Chaque équipe a ses propres pratiques - certaines ont monté un lineage "maison" (ex: équipe KTP), d'autres font du profiling technique minimal. Les règles métier ne sont pas appliquées de manière systématique.

Risque : Si non standardisé maintenant, les problèmes de qualité vont se propager à l'échelle globale via le projet LEAP.

2️⃣ Manque de Visibilité FinOps

Problème : Coûts globaux Snowflake connus, mais impossible de dire combien coûte chaque Data Product individuellement.

Impact : Pas de capacité à évaluer si le ROI d'un Data Product justifie son coût, ni à identifier les pipelines inefficaces.

Besoin : TCO par Data Product pour poser les bonnes questions sur l'alignement coût/valeur métier.

3️⃣ Data Lineage Incomplet

Deux niveaux identifiés :
• Macro (fonctionnel) : Comment les Data Products s'interfacent entre eux par domaine métier
• Micro (technique) : Comment chaque table interagit avec les autres à l'intérieur d'un Data Product

État actuel : Le lineage micro/technique n'existe pas de manière unifiée. Certaines équipes ont des solutions maison.

Impact : Difficulté à analyser les impacts en cascade, debugging complexe, pas de root cause analysis rapide.

4️⃣ Gouvernance IA/ML Non Adressée

Constat : La gouvernance technique, le FinOps et le lineage sont identifiés comme les 3 piliers prioritaires, mais la partie IA/ML reste un chantier ouvert.

Opportunité : dbt peut servir de fondation pour les initiatives IA/ML grâce à la Semantic Layer et aux Data Contracts.

Fonctionnalités Clés pour Pernod Ricard

🤖 dbt Copilot

IA intégrée qui génère automatiquement les tests et la documentation depuis vos modèles existants.

  • Ne s'entraîne PAS sur vos données (metadata uniquement)
  • Transcription des règles métier en YAML
  • Mise à jour automatique des fichiers de tests

Note : Copilot dbt ≠ GitHub Copilot, c'est un outil distinct intégré à la plateforme

💻 IDE Web & CLI

Deux options de développement pour s'adapter à tous les profils.

  • IDE Web (Studio) : Rien à installer, connexion par email/SSO, idéal pour les externes
  • CLI : Connexion de VS Code/Cursor au projet dbt Cloud pour les devs expérimentés
  • Mises à jour automatiques de l'engine, pas de problèmes de versions

→ Gain majeur pour l'onboarding des 50-70% de consultants externes

⚡ Smart Execution (State-Aware)

Optimisation automatique des runs pour ne rafraîchir que ce qui a changé.

  • ~29% d'économies en moyenne constatées
  • Réutilisation des modèles ET des résultats de tests
  • Activation en un clic dans les settings du job
  • Disponible avec dbt Fusion

→ "Rien qu'en activant ça, vous auto-payez la solution vu le nombre de modèles que vous gérez"

🔗 dbt Mesh & Cross-Database

Travail cross-projets et cross-bases de données sans perdre le découplage.

  • Référencer des modèles d'autres projets Git comme sources
  • Supporter plusieurs bases (Snowflake + BigQuery par ex.)
  • Chaque projet reste indépendant dans son orchestration
  • Triggers inter-projets configurables avec Fusion

🔗 Intégration Azure/Snowflake

Compatible avec votre stack existante sans disruption.

  • Orchestration hybride avec ADF
  • Disponible sur Snowflake Marketplace
  • Utilisation possible des crédits Snowflake
  • Aucune donnée stockée par dbt - tout reste sur Snowflake

📊 Semantic Layer

Définition centralisée des métriques métier accessible à tous les outils.

  • Cohérence des KPIs cross-équipes
  • Self-service pour Power BI
  • Single source of truth

🔍 Data Lineage Multi-Niveau

Visualisation interactive du flux de données à tous les niveaux.

  • Niveau macro : Relations entre Data Products et projets
  • Niveau micro : Tables et transformations
  • Niveau colonne : Dépendances colonne par colonne avec type de transformation (rename, passthrough, transform)
  • Impact analysis et statut des derniers runs directement dans le DAG

→ "Évite de tout casser un vendredi après-midi parce qu'on n'avait pas vu les dépendances"

📖 Catalogue & Documentation

Documentation auto-générée et toujours synchronisée avec le code.

  • Portal de documentation déployé
  • Descriptions et metadata par owner
  • Recherche full-text

Questions Techniques Soulevées

🔍 Question de Thomas : Orchestration Cross-Project avec dbt Mesh

"Comment s'assurer que quand un job d'un projet finit, ça déclenche bien les jobs dépendants dans d'autres projets sans créer de couplage fort ?"

Réponse : Avec dbt Fusion, il est possible de définir des triggers inter-projets directement dans la configuration des jobs. Un job peut avoir comme condition le succès d'un job d'un autre projet avant de s'exécuter. L'orchestration intelligente de Fusion crée une "super query" qui comprend les dépendances cross-projets.
🔍 Question de Shaïma : Rollback des modèles

"Est-ce qu'on peut faire une marche arrière si les tests échouent après un build ?"

Réponse : Oui, le versioning permet le rollback sur le code (Git) et sur les données (stratégies de snapshot pour garder N-1). À noter : le rollback données double les coûts de stockage, donc à réserver aux données critiques.
🔍 Question de Shaïma : Déploiement de la documentation

"Avec Core, on avait un HTML à déployer manuellement. C'est plus simple avec Cloud ?"

Réponse : Oui, toute la métadonnée est structurée et accessible par API. Le catalogue est automatiquement mis à jour et peut enrichir un catalogue entreprise externe.
🔍 Question de Raphaël : Impact sur les coûts Snowflake

"Si les DE font tourner leurs tests à profusion, ça peut faire exploser les coûts Snowflake ?"

Réponse : Les jobs ne sont exécutés que selon le schedule défini (ex: toutes les 12h) ou sur trigger de PR. Ce n'est pas du compute continu. De plus, l'orchestration intelligente réutilise les résultats précédents quand rien n'a changé.
